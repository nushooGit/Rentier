# Rentier Issue Register

This file is the authoritative Rentier issue-status register.

Last updated: 2026-08-06

Rules:

- Allowed statuses: `OPEN`, `AUDIT NEEDED`, `IN PROGRESS`, `IMPLEMENTED`, `VERIFIED LOCAL`, `VERIFIED PRODUCTION`, `CLOSED`, `DEFERRED`.
- `CLOSED` items must not return to the open backlog without new evidence.
- `IMPLEMENTED` is not the same as `VERIFIED`.
- Local automated, local UI, and production verification are distinct and must be recorded separately.
- Uncertainty must be recorded explicitly, never guessed.
- Evidence that cannot be confirmed is recorded as `not confirmed`.
- Every future Codex sprint must update this file before commit.

Status legend:

- `OPEN`: confirmed work remains.
- `AUDIT NEEDED`: evidence is incomplete or contradictory.
- `IN PROGRESS`: work has started but is not complete.
- `IMPLEMENTED`: code or documentation exists, but verification is not complete.
- `VERIFIED LOCAL`: verified locally by automated tests and/or local UI evidence.
- `VERIFIED PRODUCTION`: verified in production.
- `CLOSED`: complete with sufficient evidence; do not reopen without new evidence.
- `DEFERRED`: intentionally postponed.

Completion means the expected behavior is implemented, verified in the appropriate environment, and recorded here with evidence, related tests where they exist, and production verification when claimed.

## EXP-02 Audit

Scenario A is EXP-01 and is closed separately above. Scenario B asks whether an expense can involve the tenant while retaining `Fără contract` when the selected property has an active lease at the expense date.

Answers:

1. Can a tenant-involved expense be saved as `Fără contract` when an active lease exists? Yes. `SaveExpenseRequest` allows nullable `lease_id`, and when `lease_id` is null it only checks that some active lease exists for the property/date.
2. Does the form auto-select the active lease? No. The create form select uses `defaultValue={fieldValue(expense?.lease_id)}` and the empty option is `Fără contract`; it filters property leases but does not auto-select one.
3. Is `lease_id` required server-side in that situation? No. It is explicitly `nullable`, and there is no after-validation branch requiring it for tenant-involved expenses with an active lease.
4. Does edit behave the same as create? Yes. Create and edit use the same `ExpenseForm`; store and update use the same `SaveExpenseRequest`. Existing expenses with a lease keep that default, but an edit can submit null unless future validation changes.
5. What happens if multiple historical/future leases exist? The form lists all leases for the property, filtered only by property, not by expense date. Tenant options become available if any listed lease is active on the selected date. Server validation rejects a selected lease outside the expense date, but if `lease_id` is null it accepts tenant involvement as long as any active lease exists. Overlap validation should prevent multiple active leases for the same property/date through normal lease writes.
6. Are property-level owner-only expenses still valid without `lease_id`? Yes. Feature tests confirm vacant owner-paid owner-responsible expenses with null `lease_id` are accepted, and the server only applies the active-lease existence check when payer or responsible party is tenant.
7. Is this a real integrity bug, only a UX improvement, or already correctly implemented? Real integrity bug. Tenant-involved expenses can lose their lease/renter association even when the domain has an active lease context. UX auto-selection would help, but server-side integrity is incomplete.

Intended next action: tenant-involved expenses must be associated with the applicable active lease; owner-only property expenses may remain lease-less; behavior with historical/future leases must be explicitly tested.
